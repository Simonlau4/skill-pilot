## 用户以后怎么用

- **检查**：在看板按“检查更新”，或在项目目录运行 `./skill-pilot check-updates --json`；只检查，不安装。
- **更新**：在看板勾选技能并确认，或运行 `./skill-pilot update 技能名 --yes`；本轮真实目录仍受只读保护，写入验收在模拟 home。
- **三选一**：看板选择“保留我的 / 用上游的 / 交给 Codex 合并”，命令行对应 `--choice keep|upstream|merge`；合并命令先返回预览，再带回输出的 `--review` 与 `--merge-id` 确认，才会写入。
- **撤销**：在“操作记录”按“撤销”，或先用 `./skill-pilot log --json` 找到记录编号，再运行 `./skill-pilot undo 记录编号 --json`。

飞书是一整组一起勾选，并单独确认同时升级工具；命令行需要 `--confirm-lark-cli`。所有写入前都会重新核对本机状态，发现外部变化就停止并请用户刷新。每批只记录一次操作，可以撤销；脚本不会在检查或更新时运行。

## 飞书更新方案与理由

采用 **隔离安装 CLI，再直接校验官方技能包并入库**：

1. `lark-cli update --help` 和固定版本的 [官方 update 实现](https://github.com/larksuite/cli/blob/v1.0.97/cmd/update/update.go)都没有“跳过技能同步”的选项；该命令会同时处理工具与技能，所以本工具不直接调用它安装。
2. 官方实现也支持 npm 单独安装 CLI，且不自动同步技能。代码将 HOME、安装位置、缓存和 npm 配置隔离到临时目录，安装成功才把 CLI 本身放到受保护的目标位置。
3. 技能沿用 lock 中的官方来源，从 `.well-known/agent-skills/index.json` 读取当前压缩包地址和摘要，下载、校验 `sha256`、安全解包后由 Skill Pilot 更新仓库。官方 [技能同步实现](https://github.com/larksuite/cli/blob/v1.0.97/internal/skillscheck/sync.go)使用相同的索引机制。
4. 第三方安装程序没有机会接触真实助手技能根；未接入目录保持原样，安装隔离区里的额外入口随临时目录清除。CLI 文件也纳入本批备份和撤销。不会改只读来源 lock。

本轮 npm 安装流程全部通过替身验证，没有真正运行全局安装或升级，也没有执行任何技能程序。

## 边界记录与未决项

1. **真实 Codex 配置指纹差异，验收未通过**：初始和中途摘要一致，后续 `~/.codex/config.toml` 摘要发生变化。观察到修改时间为 2026-10-10 22:19:08（洛杉矶时间），文件 32,154 字节，技能停用条目 93 个，未见本轮临时目录的项目条目。工具没有调用针对该真实文件的写操作；两次 Codex 子进程的 HOME、CODEX_HOME 和缓存均为临时目录。由于初始只保存了指纹，没有复制私人配置正文，无法仅凭指纹确定改了哪些字段或由谁写入。**没有还原或覆盖该文件**，主控需要核对；不能以其他测试通过代替这项验收。
2. **旧测试清空权限开关**：第一次完整测试沿用了 `tests/test_store.py` 中将 `SKILL_PILOT_ALLOW_REAL_HOME` 临时设为空字符串的分支。它始终关闭真实写权限，只验证拒绝逻辑，没有执行真实写入，但仍不符合交接卡“不设置”的字面要求。已改为读取返回值的替身，后续完整 90 项测试通过，没有再设置该开关。没有将开关设为启用值。
3. **interview-skills 来源位置不规范**：仓库链接明确，但 `source_path` 保存的是“根目录（待核对）”。没有自行更改真实登记表或把它声称为已是最新；建议主控先核对实际目录，再按真实内容登记。
4. **官方飞书索引没有 CLI 版本锁**：官方索引提供压缩包摘要，但不提供 CLI 版本到固定技能包的独立版本映射。本方案沿用 CLI 官方使用的当前来源，并冻结用户本次看到的摘要，无法额外证明技能包与任意未来 CLI 版本一一绑定。建议 PLAN 明确沿用官方当前索引的口径；若要求严格的历史配套，需上游提供版本化索引。
5. **三方合并的实际边界**：文本变化可合并；非文本文件或特殊入口的变化不交给 Codex 猜测。当前会明确提示改选保留我的或上游版本；文件夹外入口会阻止安装。建议 PLAN 补充这一点。
6. **真实检查的开发迭代**：初次检查因逐文件延迟下载而中止；第二次检查暴露 GitHub 对直接批量取文件对象的兼容问题，保存在 `work/m4-check-download-failure.json`；修正为一次获取默认分支历史和对象后完成最终检查，原先的下载错误全部消除。重复是由新失败触发，没有在通过后重复同一项检查。所有下载、缓存、解包、合并和浏览器运行区都在系统临时目录；结束后清除运行区，交付证据留在项目 work 中。

PLAN.md、依赖判定表和真实来源登记均未修改。本轮没有开始 M5 或之后的里程碑，没有安装系统入口，没有提交或推送项目。
